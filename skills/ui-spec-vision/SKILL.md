# UI-Spec Vision:分类分区式 UI-Spec 提取

本 skill 解决的核心问题:**中等规模多模态模型(如 Qwen3.6-27B)对整页截图做单遍分析时,小字号文本、间距数值、图标细节、组件状态会大量丢失或臆造**。解决方案借鉴 VisualRepair(arXiv:2607.14075)的两个机制:

1. **图片类型分类 → 分支处理链**(对应 ITTC):不同类型的输入图走不同的预处理与分析路径,不搞一刀切。
2. **全局骨架 → 区域聚焦 → 自适应放大**(对应 DTRF):先低倍看结构,再裁剪放大看细节,低置信区域二次放大复检。

**铁律:禁止对整图做单遍分析后直接输出 UI-Spec。** 任何细节字段(字号、间距、颜色值、图标名)只允许来自裁剪放大后的区域分析,不允许来自整图第一印象。

## 依赖

- Node.js ≥ 14 + jimp(在 `scripts/` 目录执行 `anpm install`,依赖已锁定为 `jimp@0.22`)
- 选 jimp 而非 sharp 的原因:jimp 为纯 JS 实现,无原生二进制依赖,规避端点安全软件对非白名单二进制的路径限制,内网 anpm 可直接安装
- 本 skill 附带 `scripts/crop.js`,所有裁剪/放大/网格叠加/长图切片操作统一用它,不要临时手写图像处理代码。若执行报错 `Cannot find module 'jimp'`,先在 `scripts/` 目录执行 `anpm install` 再重试。

## 工作流

### 第 0 步:图片预检

先用 `scripts/crop.js info <图片路径>` 获取尺寸,然后看一眼原图,输出图片类型判定(只判定,不分析内容):

| 类型 | 判定特征 | 处理链 |
|---|---|---|
| A. 高保真设计稿 | 像素规整、无浏览器 chrome、留白精确 | 标准链(第 1–4 步) |
| B. 真实页面截图 | 有浏览器边框/滚动条/真实数据噪声 | 标准链,但 spec 中标注"数据为示例值",样式数值置信度整体降一级 |
| C. 低保真线框图 | 灰盒、占位符、手绘感 | 只提取布局结构与组件类型,**跳过**颜色/字号/精确间距字段,spec 中显式留空 |
| D. 局部组件截图 | 尺寸小、单一组件 | 跳过第 1 步全局分析,直接进入第 2 步单区域深挖 |
| E. 长页面截图 | 高宽比 > 2.5 | 先 `crop.js slice` 纵向切片(带 10% 重叠),每片按标准链处理,最后合并时对重叠带去重 |
| F. 多状态拼图 | 同一组件多个状态并排 | 先切分为单状态图,各自按 D 处理,合并为同一组件的 states 数组 |

如果一张图混合多种类型(如设计稿旁边贴了标注文字),把标注区域单独裁出,作为约束条件参与后续分析而非视觉内容。

### 第 1 步:全局骨架分析(zoom-out)

用 `scripts/crop.js grid <图片路径>` 生成带编号网格叠加图(默认 6×8 格),看**网格版**而非原图,输出:

1. 页面级布局模式:如 顶栏+侧栏+内容区 / 上下结构 / 居中卡片式
2. 区域清单:每个区域给出名称、用网格坐标描述范围(如 `B2:E5` 表示列 B–E、行 2–5)、区域类型(导航/表单/表格/卡片列表/工具栏/图表/其他)
3. 区域间关系:栅格列数、区域间距的粗略档位(紧凑/常规/宽松)

**为什么用网格坐标而不是像素坐标:模型直接估算像素 bbox 不可靠,网格格子引用 + 脚本换算才是可信路径。** 此步骤禁止输出任何细节字段。

### 第 2 步:区域聚焦分析(zoom-in)

对第 1 步的每个区域,依次执行:

```bash
node scripts/crop.js cut <原图> --cells B2:E5 --scale 2 -o region_01.png
```

`--cells` 直接接受网格坐标,脚本负责换算像素并按 `--scale` 放大(默认 2 倍,区域越小放大倍数越高,上限 4)。然后看裁剪图,对该区域输出:

- **组件识别**:映射到 uecp 组件名(优先)或 antd 组件名(uecp 无对应时),含组件层级嵌套关系
- **文本内容**:逐字提取,不许概括。表格提取表头全量 + 前 2 行示例数据
- **样式细节**:字号档位、圆角、边框、阴影有无
- **色值(必须走脚本取色,禁止目测报 hex)**:
  - 大面积色(背景/填充/分割线):`node scripts/crop.js pick <原图> --cells <格子>` 输出区域主色直方图,取占比最高的对应项
  - 精确点色(文字/图标/边框):模型在裁剪图上指认采样点的相对坐标(选笔画/色块中心,避开边缘抗锯齿带),执行 `node scripts/crop.js pick <裁剪图> --at x,y`;若脚本警告中心像素与邻域众数不一致,换点重采
  - 脚本返回的 hex 为像素级精确值,可标 `high` 置信;但若原图为 jpg 等有损格式,注明"含压缩偏移,需与 design token 对表收敛"
- **间距**:相邻元素间距估值,标注为 4px 栅格系统的倍数(8/12/16/24…)
- **状态线索**:禁用态、选中态、hover 残留、校验错误、加载态、空态
- **每个字段附置信度**:`high` / `medium` / `low`

### 第 3 步:低置信复检(自适应二次放大)

收集第 2 步所有 `low` 置信字段,对其所在子区域再裁剪 + 放大(在区域图基础上继续 `crop.js cut`,总放大不超过 4 倍)。复检后:

- 看清了 → 更新字段值,置信度升级
- 仍看不清 → 保留 `low`,值标注为 `null`,并在 spec 的 `open_questions` 列表写明该项待人工确认

复检最多一轮,不许无限迭代。**看不清就承认看不清,臆造一个数值是本流程最严重的失败模式。**

### 第 4 步:合并输出 UI-Spec

跨区域一致性处理后输出最终 spec:

1. **Token 归并**:各区域颜色/字号/间距去重收敛为 `design_tokens`,区域内改为引用 token(色值相差 ≤ 一个色阶的合并为同一 token)
2. **组件复用检测**:视觉相同的组件实例合并定义,实例只记录差异 props
3. **矛盾消解**:同一 token 在不同区域取值冲突时,以放大倍数更高的区域分析结果为准

输出格式(如项目已有内部 UI-Spec schema,以内部 schema 为准,以下为缺省结构):

```yaml
meta:
  source_image: xxx.png
  image_type: A  # 第 0 步判定结果
  analysis_passes: 3
layout:
  pattern: sidebar-layout
  grid: {columns: 24, gutter: 16}
design_tokens:
  colors: {primary: "#009966", ...}
  font_sizes: {body: 14, title: 16, ...}
  spacings: [8, 16, 24]
regions:
  - id: header
    grid_cells: "A1:F1"
    components:
      - component: uecp/Menu
        props: {mode: horizontal}
        confidence: high
        children: [...]
texts:            # 全量文本清单,供生成阶段直接引用,防止改写
  - {region: header, text: "工作台", confidence: high}
states: [...]     # 捕获到的组件状态
open_questions:   # 复检后仍不确定的项
  - "侧栏折叠态未在图中体现,需确认是否支持"
```

## Qwen3.6-27B 专项注意事项

- **一步一图**:每轮分析只看一张图,禁止同时贴多张裁剪图对比——上下文中多图会显著降低细节提取质量。需要对比时,分两轮各自提取后在文本层面比对。
- **不要向模型要像素坐标**:所有定位走网格坐标,换算交给脚本。
- **文字提取优先于样式提取**:同一区域先做文本转录再做样式分析,分两次看图。混在一问里文字漏抄率明显升高。
- **色值分工**:模型只负责指认采样位置和判断颜色用途(主色/文字色/边框色),hex 值一律由 `crop.js pick` 读取,禁止模型目测输出十六进制。
- **长上下文防漂移**:区域数量 > 8 时,每完成 3 个区域就把已产出的区域 spec 写入临时文件落盘,最后从文件合并,不依赖上下文记忆。

## 与下游生成阶段的衔接

- UI-Spec 是唯一交接物:生成阶段只读 spec,不回看原图。如生成时发现 spec 信息不足,回到本 skill 补分析对应区域,而不是让生成模型自己看图脑补。
- `open_questions` 非空时,先向用户确认再进入生成,或在生成代码中以 TODO 注释显式标记。
