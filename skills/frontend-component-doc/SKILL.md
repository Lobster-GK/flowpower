# 组件文档生成

输出必须使用中文。本 skill 只生成或更新组件文档，不修改组件代码、不执行质量检查。

目标是把组件代码中真实存在的能力整理成组件库式文档：先让使用者快速知道它能做什么、怎么引入、怎么用，再用简洁 API 表格补足细节。文档要忠于源码；源码无法确认的信息写“未在源码中确认”，不要补全成看似合理的 API。

## 输入

优先读取用户指定的：

- 组件主文件，例如 `Button.tsx`、`SearchForm.vue`。
- 组件目录中的 `index.ts`、类型文件、样式文件、hooks、子组件。
- 已有 README、Storybook stories、demo、测试文件。
- 项目资产中和组件规范、文档规范、样式 token 相关的 Markdown。

如果用户没有指定组件路径，先要求用户提供路径或组件名。不要全项目搜索相似组件来猜。

## 产物

默认写入用户指定文档路径。如果用户没有指定，优先写入组件同目录：

```text
<component-dir>/<ComponentName>.docs.md
```

如果项目已有组件文档约定，以项目约定为准。无法写文件时，在回复中输出完整 Markdown，并说明未能持久化的原因。

## 工作流程

1. 读取入口文件、导出方式、类型定义、样式、demo/story/test。
2. 提取公共使用面：组件用途、核心 props、事件、children/slot、状态、样式入口。
3. 根据 JSX/模板和样式关系绘制 ASCII 结构原型图。
4. 先写可运行的最小示例，再补典型场景示例。
5. 用简洁表格写 API；无法确认的字段不要写进正式 API。
6. 交付前自查示例是否只使用已确认 API、文档是否遗漏关键状态、ASCII 图是否能从源码反查。

## 事实规则

- TypeScript 类型、interface、type、泛型、默认值和 JSDoc 是 API 的最高优先级事实来源。
- JSX/模板结构、条件渲染、状态分支、className/style、样式文件用于判断结构、状态和样式入口。
- story、demo 和测试只能作为使用方式证据，不能覆盖组件源码。
- 发现源码和 demo 不一致时，在 `FAQ / 注意事项` 中说明，不要静默合并。
- 不要在 API 表格里放“来源”列；来源用于内部判断，只有存在不确定或冲突时才在注意事项中说明。

## 文档结构

按下面结构输出。没有信息的可选章节可以省略，但 `简介`、`导入`、`结构原型`、`代码演示`、`API` 必须保留。

```markdown
# ComponentName

## 简介

## 何时使用

## 导入

## 结构原型

## 代码演示

## API

## 设计与样式

## FAQ / 注意事项
```

## 章节要求

### 简介

用一到两段说明组件解决什么问题、主要能力是什么。不要写营销式长文。

### 何时使用

列出 3 到 5 条真实适用场景。不要为了凑数写空泛描述。

### 导入

写真实导入方式。无法从源码确认导出路径时，使用：

```tsx
import { ComponentName } from "<按项目导出路径调整>";
```

### 结构原型

用 ASCII 码绘制组件结构示意图。它表达区域和相对关系，不表达像素级视觉。

```text
+--------------------------------------+
| component-root                       |
| label                    action      |
| +----------------------------------+ |
| | content / children               | |
| +----------------------------------+ |
| help / error / extra                 |
+--------------------------------------+
```

绘制规则：

- 只表达组件主要区域、slot/children、关键元素、状态区域和相对位置。
- 使用源码中能确认的区域名、className、data-testid、子组件名或语义化自拟 ID。
- 不表达像素尺寸、精确间距、颜色、阴影、圆角或真实比例。
- 组件有 loading、empty、error、disabled、expanded、selected、open 等重要状态时，必要时补充小型状态图。
- ASCII 图里的每个区域或元素必须能在源码、模板、样式或 API 中找到依据；无法确认时标注 `unknown`。

### 代码演示

至少包含 `基础用法`。如果源码、demo 或 story 能确认更多典型场景，再补充 `不同状态`、`受控用法`、`自定义渲染`、`组合使用` 等示例。

示例规则：

- 示例优先于 API 表格出现，让使用者先看到怎么用。
- 只使用源码中确认存在的 props、事件和 children/slot。
- 不发明业务字段、接口请求或复杂上下文。
- 如果组件必须依赖 Provider、Form、Router 或主题上下文，示例要写出最小包裹方式。
- 示例代码保持短小；一个示例只展示一个核心用法。

### API

使用组件库常见的简洁表格。React props、Vue props、事件、slot、暴露方法按实际情况分组；没有的分组不要写。

Props 表格：

| 参数 | 说明 | 类型 | 默认值 | 必填 |
| --- | --- | --- | --- | --- |

事件 / 回调表格：

| 事件名 | 说明 | 参数 |
| --- | --- | --- |

Slots / Children 表格：

| 名称 | 说明 | 类型 |
| --- | --- | --- |

暴露方法 / 静态成员表格：

| 名称 | 说明 | 类型 |
| --- | --- | --- |

API 写法规则：

- 只写对使用者有意义的公共 API，不展开内部变量、内部 hooks、私有子组件。
- 联合类型、枚举值、尺寸、主题、状态类 props 要写清可选值。
- 默认值只有能从源码或类型明确确认时才写；否则写 `-`。
- props 很多时按功能分组，例如 `基础属性`、`状态属性`、`渲染定制`、`样式属性`，不要生成难以阅读的超长单表。
- 复杂类型可以保留类型名，并在表格后用短代码块补充类型定义。

### 设计与样式

只在源码中能确认样式入口时输出。说明 className、style、CSS Module、Less/Sass、Tailwind、styled、CSS variable、design token 等使用方式，以及外部可以安全覆盖的样式入口。

### FAQ / 注意事项

放少量真正影响使用的内容，例如：

- 源码和 demo/story/test 不一致。
- 默认值、导出路径、样式入口未在源码中确认。
- 需要 Provider、Form、Router、主题上下文或运行时环境。
- 不建议的使用方式或容易踩坑的状态组合。

不要输出大段源码依据表或覆盖率检查表，除非用户明确要求。
