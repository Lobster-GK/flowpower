# 根据错误修复

本 Skill 的目标不是“看到错误就立刻改代码”，而是以可审计、可回滚、最小影响的方式修复明确错误。必须先分析，再制定修改计划，最后实施。

## 适用输入

必须存在明确错误来源，例如：

- lint/typecheck/build 输出。
- 启动失败日志。
- 浏览器运行时错误、控制台错误或网络错误。
- UI 审查给出的明确偏差。

如果存在 `03-codegen-plan-spec.md`，必须先读取它，并把其中的任务类型、File Plan、Implementation Steps、验证方式作为修复边界。计划缺失时，才在本 skill 内输出简短错误分析和修改计划。

如果缺少错误报告、失败命令、文件路径、错误现象或复现方式，不要猜测性修改代码。先要求补充信息，或只做只读排查并说明还缺什么。

## 修复原则

- 只修复当前错误报告中的阻塞问题，不追逐无关 warning。
- 优先修改本次生成或本次任务明确相关的文件。
- 只有当错误明确指向共享配置、service、类型定义或项目公共代码时，才允许修改这些文件。
- 不做无关重构、风格统一、依赖升级、目录迁移或大范围重写。
- 不通过删除功能、吞掉异常、注释掉校验、降低类型约束、扩大 `any`、关闭 lint 规则来掩盖问题，除非用户明确要求并理解代价。
- 修复必须保持原需求、UI 规格、接口契约和项目资产约束不变。
- 如果存在多个可能根因，先选择证据最充分、影响最小的修复路径。
- 修复说明和新增注释使用中文；代码标识符、文件路径、API 字段和 JSON key 保持英文。

## 执行流程

### 1. 收集证据

先读取并整理错误报告中的关键信息：

- 失败命令或检查阶段。
- 完整错误消息。
- 文件路径、行号、规则编号、堆栈或短上下文。
- 失败是否稳定复现。
- 关联的生成文件、目标目录、route、rootDomId 或接口文档。

如果错误报告中给出的文件路径不存在，先确认路径是否移动或产物是否未生成，不要直接创建不相关文件。

### 2. 根因分析

修改前必须先输出简短分析，说明：

- 错误表面现象是什么。
- 最可能根因是什么。
- 证据来自哪条日志、哪段代码或哪个文件。
- 影响范围有哪些文件。
- 是否存在不确定项。

如果不确定项会影响修复方向，先停止并向用户提问；如果不确定项不影响最小修复，可以记录假设后继续。

### 3. 制定修改计划

实施前必须先输出修改计划。计划应包含：

- 准备修改哪些文件。
- 每个文件为什么需要改。
- 预计采用什么修复方式。
- 哪些文件明确不会改。
- 修复后要交回哪个检查阶段或执行什么验证。

计划要短，但必须足够让用户或主模型看出修改范围。不要在没有计划的情况下直接编辑文件。

如果已经读取到 `03-codegen-plan-spec.md`，不要重复发明另一套计划；只确认该计划仍可执行。若错误证据和计划冲突，停止并说明需要更新计划。

### 4. 实施最小修改

按计划修改代码：

- 每次只围绕当前根因做最小必要改动。
- 修改时保留现有结构和局部风格。
- 如果实施过程中发现计划不成立，停止继续扩大修改，先更新分析和计划。
- 不要顺手修复未被当前错误报告阻塞的问题。

### 5. 验证或回交

修改完成后，优先交回触发错误的同一个检查阶段重新执行，例如：

- lint 错误交回 `frontend-lint-check`。
- 启动错误交回 `frontend-boot-check`。
- 运行时错误交回 `frontend-runtime-check`。
- UI 偏差交回 `frontend-ui-review`。

如果当前环境无法运行验证，必须说明未验证原因，并给出建议执行的命令或阶段。

### 6. 总结结果

最终输出必须包含：

- 根因摘要。
- 修改文件列表。
- 每个文件的关键修改点。
- 已执行或建议执行的验证。
- 剩余风险或需要用户确认的问题。

## 输出格式

修复前先输出：

```text
错误分析：
- ...

修改计划：
- ...
```

修复后输出：

```text
修复结果：
- ...

验证：
- ...

剩余风险：
- ...
```
