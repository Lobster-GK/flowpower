# frontend-codegen-plan 描述

## 干什么用

用于生成或更新 `03-codegen-plan-spec.md`。它是在前端写代码、改代码或修复错误之前形成的持久化执行契约，把用户目标、现有代码、错误证据、可选 UI specs 和项目资产转成任务类型、事实来源、变更范围、文件计划、实施步骤、状态/数据/样式策略、业务交互契约、需求或错误到代码的映射、风险和验证方式。

## 什么时候用

- 新页面、新组件、截图还原或大幅 UI 结构变更已经有 `01-ui-layout-spec.md` 和 `02-component-mapping-spec.md`，准备生成 `03-codegen-plan-spec.md`。
- 修改已有页面、组件或功能前，需要先明确会读哪些文件、改哪些文件、按什么步骤改、哪些范围不碰。
- 修复 bug 前，需要把错误现象、复现路径、日志/堆栈、相关代码、根因假设、修复步骤和回归验证写成计划。
- 新增局部需求或小范围重构前，需要让后续 `frontend-ui-codegen` 有稳定、可追踪、可恢复的实施依据。
- 页面包含提交、查询、删除、跳转、刷新、重试、上传等交互，需要明确预期业务结果、API/路由/数据/权限依赖、UI 状态变化、证据来源和确认状态。
- 担心多轮对话或上下文压缩丢失计划时，需要把计划落到文件。

## 什么时候不用

- 不用于直接写代码、分析截图、生成布局说明、生成组件映射、接口设计、lint、启动检查或运行时检查。
- 新 UI 或大幅 UI 变更缺少 layout spec/component mapping spec，或组件映射覆盖验证失败时，不要继续生成实施计划。
- 现有功能变更或 bug 修复无法定位目标文件、关键证据缺失且没有可执行诊断路径时，不要编造计划。
- 本轮要求真实可用的关键交互仍缺少业务契约时，不得用截图、常见经验或假成功逻辑补齐计划。
- 只需要执行已有检查命令、查看日志或做一次性说明时，不需要生成 plan spec。
