# 单测生成 Skill

## 目标

为指定代码生成稳定、可运行、可维护的单元测试。

本 Skill 的首要目标不是一次性追求高覆盖率，而是：

1. 先生成最小可运行测试。
2. 再按需补充主流程和边界场景。
3. 测试失败时先分类原因，再决定是否修复。
4. 严禁无限循环修复。
5. 默认只修改测试文件，不随意修改业务源码。

---

## 适用场景

当用户要求生成、补充、修复或优化单元测试时，使用本 Skill。

适用于：

* 工具函数单测
* React 组件单测
* React Hook 单测
* Vue 组件单测
* service / api / adapter 层单测
* 普通业务逻辑函数单测
* 已有单测失败后的分析和修复

不适合直接生成复杂单测的场景：

* 被测文件依赖过多，需要大量 mock 才能运行
* 强依赖浏览器全局对象、iframe、微前端容器或运行时注入对象
* 强依赖后端接口、登录态、权限上下文
* 组件没有稳定选择器，且交互链路复杂
* 测试环境本身缺失或配置明显错误

遇到不适合直接生成复杂单测的场景，应先生成最小 smoke test，或输出测试建议，不要强行生成大量用例。

---

## 总体原则

### 1. 先跑通，再增强

不得一开始生成大量复杂测试用例。

首轮最多生成 1-3 个测试用例：

1. smoke test：验证被测对象可以正常加载、渲染或调用。
2. 主流程测试：验证最核心的正常业务路径。
3. 简单边界测试：只覆盖一个清晰边界。

如果 smoke test 都无法通过，不允许继续补充复杂 case。

---

### 2. 优先模仿已有项目风格

生成测试前必须先检查项目已有测试风格，包括：

* 测试文件命名规则
* 测试文件目录结构
* mock 写法
* setup 文件
* alias 配置
* package.json 中的 test 脚本
* 已有相似模块的测试文件

必须优先模仿项目已有写法。

禁止凭空引入项目中不存在的测试库。

---

### 3. 默认只修改测试文件

默认情况下，只允许新增或修改测试文件。

禁止直接修改：

* 业务源码
* 公共工具函数
* 构建配置
* 测试框架配置
* package.json
* lock 文件

只有在明确判断为被测代码真实 bug，且用户允许修改源码时，才可以修改业务代码。

如果发现源码可能存在问题，应先说明原因，不要直接修改。

---

### 4. 每次只解决一个问题

测试失败后，不允许一次性做大范围修改。

每次修复只能针对一个明确原因，例如：

* import 路径错误
* mock 数据结构错误
* 异步等待错误
* 断言不匹配
* 测试环境缺少浏览器 API mock

禁止在一次修复中同时改动大量 mock、断言、测试结构和被测代码。

---

### 5. 必须设置修复上限

同一个测试文件最多自动修复 5 次。

如果第 5 次修复后仍然失败，必须停止继续修复，并输出：

1. 当前失败原因
2. 已经尝试过的修复
3. 失败可能属于哪一类问题
4. 建议人工确认的点
5. 当前测试文件建议保留、简化还是回滚

严禁无限循环运行和修复。

---

## 执行流程

### 第一步：识别测试环境

生成单测前，先检查项目测试环境。

必须查看：

1. `package.json`
2. 已有测试文件

需要确认：

* 使用什么测试框架
* 使用什么断言库
* 是否有 jsdom 环境
* 是否有 React Testing Library / Vue Test Utils
* 是否配置了 alias
* 是否已有统一 mock 方案
* 当前项目推荐的测试命令是什么

如果无法确认测试框架，不要猜测，应先从 package.json 和已有测试中推断。

---

### 第二步：分析被测文件

生成测试前，必须分析被测文件：

1. 被测对象是什么类型：

   * 函数
   * 类
   * React 组件
   * React Hook
   * Vue 组件
   * service
   * api
   * 工具模块
2. 输入是什么
3. 输出是什么
4. 是否有副作用
5. 是否有异步逻辑
6. 是否依赖外部模块
7. 是否依赖浏览器 API
8. 是否依赖全局变量
9. 是否依赖上下文，例如 router、store、theme、i18n、权限、微前端容器
10. 是否已经存在测试文件

---

### 第三步：判断测试复杂度

根据依赖和运行难度，将测试复杂度分为低、中、高。

#### 低复杂度

特征：

* 纯函数
* 工具函数
* 输入输出明确
* 无复杂外部依赖
* mock 很少或不需要 mock

策略：

* 可以生成 smoke test、主流程、简单边界测试。
* 首轮最多 3 个 case。

#### 中复杂度

特征：

* 有少量外部依赖
* 有异步逻辑
* 有简单组件渲染
* 需要少量 mock

策略：

* 第一轮只生成 smoke test。
* smoke test 通过后，再补主流程。
* 每次只新增少量 case。

#### 高复杂度

特征：

* mock 超过 5 个外部依赖
* 依赖复杂上下文
* 依赖微前端运行时
* 依赖登录态、权限、后端接口
* 初始化副作用明显
* 测试环境缺失

策略：

* 不直接生成完整单测。
* 只生成最小 smoke test，或输出测试建议。
* 不为了通过测试堆叠大量 mock。

---

### 第四步：生成最小可运行测试

首轮测试必须尽量简单。

对于函数：

* 只验证一个最核心输入输出。
* 不覆盖过多边界。
* 不制造复杂 mock。

对于组件：

* 优先验证可以正常 render。
* 使用项目已有的 render 工具。
* 不优先测试复杂交互。
* 不依赖不稳定的 DOM 结构。
* 优先使用用户可感知文本、role、label。
* 不要滥用 className 或深层 DOM 选择器。

对于 Hook：

* 使用项目已有 hook 测试方式。
* 优先验证初始状态或简单调用。
* 不直接构造复杂上下文，除非项目已有封装工具。

对于 service/api：

* 优先 mock 请求层。
* 只验证请求参数和返回结果处理。
* 不真实请求后端。
* 不测试第三方库内部行为。

---

### 第五步：运行测试

只运行当前测试文件。

---

## 失败处理流程

测试失败后，必须先分析失败日志，不允许直接修改。

### 失败分类

必须将失败归类为以下类型之一：

1. 语法错误
   例如 import 错误、括号错误、类型错误、API 使用错误。

2. 环境错误
   例如 jest/vitest 配置错误、jsdom 缺失、babel/tsconfig 问题、alias 解析失败。

3. mock 错误
   例如依赖未 mock、mock 返回结构错误、异步 mock 不完整。

4. 断言错误
   例如测试预期和实际业务逻辑不一致。

5. 异步错误
   例如没有 waitFor、没有 await、定时器未处理、Promise 未 resolve。

6. 选择器错误
   例如 DOM 查询方式不稳定，文本不存在，role 不匹配。

7. 被测代码问题
   例如源码真实存在 bug。

8. 当前文件不适合自动化单测
   例如依赖过多、上下文过重、需要真实运行容器。

---

### 失败后必须输出判断

每次失败后，先输出：

```md
失败类型：
失败原因：
是否需要修改测试文件：
是否需要修改业务源码：
是否需要修改配置：
本次只准备修改什么：
```

然后再执行修复。

---

### 修复策略

优先级如下：

1. 修正明显语法错误。
2. 修正 import 或路径问题。
3. 简化测试用例。
4. 简化断言。
5. 减少复杂 mock。
6. 补充必要的最小 mock。
7. 处理异步等待。
8. 如果属于环境问题，停止继续改测试，输出配置建议。

测试失败后，优先缩小测试，而不是扩大测试。

禁止为了让测试通过不断堆叠 mock。

---

## 修复次数限制

同一个测试文件的同一个错误最多自动修复 2 次。

计数规则：

* 第一次测试失败后的修改，记为第 1 次修复。
* 第二次测试失败后的修改，记为第 2 次修复。
* 第 2 次修复后仍失败，必须停止。

停止时输出：

```md
## 单测生成已停止

### 当前状态

测试仍未通过。

### 失败类型

说明失败属于哪一类。

### 已尝试修复

列出已经尝试的修复动作。

### 当前判断

说明继续自动修复的风险。

### 建议人工确认

列出需要人工确认的配置、依赖、业务逻辑或测试环境问题。

### 建议处理方式

说明建议保留当前测试、简化测试，还是回滚测试文件。
```

---

## 成功后的增强策略

只有当前测试文件通过后，才允许补充更多 case。

增强顺序：

1. 主流程 case
2. 简单边界 case
3. 异常 case
4. 异步 case
5. 复杂交互 case

每新增一批 case，都必须重新只运行当前测试文件。

如果新增 case 导致失败，应优先回退新增 case，而不是破坏已经通过的基础测试。

---

## 禁止行为

严禁以下行为：

1. 无限循环修复。
2. 一次性生成大量测试用例。
3. 未识别测试框架就直接写测试。
4. 凭空引入项目中不存在的测试库。
5. 为了让测试通过随意修改业务源码。
6. 为了让测试通过修改 package.json 或 lock 文件。
7. 为了提高覆盖率牺牲测试稳定性。
8. 大量堆叠 mock。
9. 直接测试第三方库内部行为。
10. 使用不稳定的深层 DOM 选择器。
11. 忽略失败日志直接猜测修复。
12. 全量运行测试导致耗时过长。
13. 在 smoke test 未通过前继续补充复杂 case。

---

## 输出要求

生成或修复单测后，需要输出简短总结：

````md
## 单测处理结果

### 新增/修改文件

- xxx.test.ts

### 测试内容

- 覆盖了什么场景
- 是否只是 smoke test
- 是否包含主流程或边界场景

### 执行命令

```bash
xxx
````

### 执行结果

* 通过 / 失败

### 如果失败

* 失败类型
* 当前原因
* 已修复次数
* 是否已停止自动修复

```

---

## 推荐策略

始终遵循：

> 可运行性优先于覆盖率。  
> 简单测试优先于复杂测试。  
> 失败分类优先于盲目修复。  
> 止损优先于无限循环。  
> 模仿项目已有风格优先于创造新风格。
```
