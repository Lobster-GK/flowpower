# frontend-ui-layout-spec 描述

## 干什么用

用于生成或更新 `01-ui-layout-spec.md`。它把一张或多张截图、UI 图片、文字 UI 需求或已有页面描述整理成页面事实清单，包括页面区域、布局树、ASCII 结构原型图、所有肉眼可见 UI 内容、稳定元素 ID、相对位置、关键样式、文案、视觉状态、可见交互线索、分隔结构、布局约束、视觉 token、资产、多图状态差异、页面状态覆盖和覆盖检查。

它强调“可见内容不可遗漏”：区域标题、说明文字、提示语、状态文案、图标、分隔线、特殊区域内容等，即使没有交互，也必须作为独立元素编号、定位并描述关键样式；无法判断用途时保留为 unknown 元素，不要省略。

识别时固定按“从上到下、从左到右、从外到里”的顺序，逐区域检查文字、图片/资产、布局和层级四类事实。遇到表单、列表、表格、分页、重复内容、浮层或移动端页面时，还会按专项清单检查常见遗漏；同时评估默认、空、加载、错误、提交中、成功/失败等适用状态，未提供视觉证据时只记录需要确认的状态，不虚构 UI。

它会为按钮、输入框、选择控件、返回、关闭等记录可见交互线索，但截图只能证明交互入口，不能证明点击后的接口、路由、数据变更、权限规则或业务结果。

在多 agent UI 识别模式下，每个子 agent 必须针对全部输入独立输出一份章节完整、ID 稳定、覆盖检查通过的 `agent-local final` layout spec，而不是观察草案。主模型把多份完整答案按语义对齐后交叉补缺、复核冲突，生成唯一 `canonical final`。当 `multiAgent.options.includeComponentMapping=true` 时，每个 agent 还可以单独输出非权威组件映射建议。

## 什么时候用

- 用户要做“截图还原”“图片生码”“文字生成页面”，但还没有进入正式组件映射和写代码阶段。
- 用户提供多张图片，描述同一个页面的不同状态、弹窗、抽屉、空态、错误态、选中态或滚动位置。
- scene template 或本次命令明确启用多 agent 识别，需要多个同职责 agent 并行完成同一批输入的完整最终答案，再由主模型交叉合并。
- 需要用 ASCII 结构原型图表达页面整体空间关系，辅助后续组件映射、生码计划和代码生成。
- 场景流程需要先确认页面上有什么、怎么排、每个可见元素在哪里、有哪些关键样式，再交给 `frontend-component-mapping-spec`。
- 需要系统检查表单、列表、表格、分页、浮层、重复内容或移动端专项元素，降低识别遗漏。
- 需要确认页面默认、空、加载、错误、提交中、成功/失败等适用状态是否已有视觉证据。
- 需要识别影响后续组件映射的不确定项，并把问题写进 `Open Questions`。

## 什么时候不用

- 普通模式下不用于选择最终组件库组件，不归属最终 props、事件、状态、数据字段或接口字段。
- 不用于直接生成代码、接口集成、lint、启动检查、运行时检查或 UI review。
- 不用于普通图片描述、非 UI 图片、后端任务，或没有前端实现意图的视觉分析。
- 已经有清晰可用的 `01-ui-layout-spec.md`，只需要做组件映射、计划、改代码或修 bug 时，不要重复使用。
